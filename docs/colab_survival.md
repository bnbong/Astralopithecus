# Colab 세션 생존 설계

담당은 준혁입니다. Colab 런타임을 조작하는 사람은 한 명으로 유지합니다. 다른 팀원은 노트북을
열어 볼 수는 있지만 실행 중인 가상 머신은 공유되지 않으므로, 진행 상황은 Drive에 저장된 로그로만
확인합니다.

이 문서는 세션이 끊기는 상황을 전제로 실행을 설계하는 방법을 설명합니다. 끊기지 않게 만드는 것이
아니라, 끊기더라도 손실이 몇 분치에 그치도록 만드는 것이 목표입니다.

## 1. 무엇이 살아남고 무엇이 죽는지

정확히 구분해야 밤샘 실행을 맡길지 판단할 수 있습니다. 오래 걸리는 작업은 모두
`python -m vqa.jobs start` 로 부모 프로세스에서 분리해서 띄웁니다.

분리된 프로세스가 살아남는 상황은 다음과 같습니다.

- 노트북 셀을 중단했을 때에도 계속 실행됩니다.
- 브라우저 탭을 닫았을 때에도 계속 실행됩니다.
- 노트북 화면과 런타임 사이의 연결이 일시적으로 끊겼을 때에도 계속 실행됩니다.

분리된 프로세스도 함께 죽는 상황은 다음과 같습니다.

- 유휴 시간 초과로 런타임이 회수되면 함께 종료됩니다.
- 최대 연속 실행 시간에 도달하면 함께 종료됩니다.
- compute unit이 소진되면 함께 종료됩니다.
- 자원 사정으로 인스턴스가 선점되면 함께 종료됩니다.
- 사용자가 런타임을 직접 종료하거나 다시 시작하면 함께 종료됩니다.

Pro+ 구독은 백그라운드 실행을 제공한다고 안내되어 있습니다. 다만 실제 계정과 실제 런타임에서
어떻게 동작하는지는 안내 문구만으로 확정할 수 없으므로, D1에 직접 확인해야 합니다. 확인 절차는
아래 2절에 있습니다.

세션을 유지하겠다고 자동 클릭 스크립트나 가짜 입력을 만드는 방법은 사용하지 않습니다. Colab
이용 약관에 어긋나고, 계정이 제한되면 팀 전체의 GPU 경로가 사라집니다. 대신 checkpoint를 Drive에
자주 남겨서 언제 끊기더라도 이어서 실행할 수 있게 만드는 방식으로 대응합니다.

## 2. 백그라운드 실행 확인 절차

D1에 한 번만 수행합니다. `21_colab_27b_run.ipynb` 의 1번 절에 이 절차를 실행하는 셀이 있습니다.

1. 시험용 job을 띄웁니다. 이 job은 15분 동안 1분마다 Drive의 파일에 현재 시각을 기록합니다.
2. 브라우저 탭을 완전히 닫습니다. 창을 최소화하거나 다른 탭으로 옮기는 것이 아니라 탭 자체를
   닫아야 합니다.
3. 10분 정도 지난 뒤에 다시 접속합니다.
4. 확인 셀을 실행해서 기록된 시각 사이에 빈 구간이 있는지 봅니다.

판정 기준은 다음과 같습니다. 기록이 1분 간격으로 끊김 없이 이어지면, 탭을 닫아도 실행이 유지되는
것이므로 야간 실행을 맡길 수 있습니다. 탭을 닫은 시점부터 기록이 멈췄다가 다시 접속한 시점부터
재개되었다면, 백그라운드 실행이 동작하지 않는 것입니다. 이 경우에는 탭을 열어 둔 채로 실행하고,
checkpoint 저장 간격을 짧게 잡아야 합니다.

확인 결과는 팀 채널에 반드시 공유합니다. 이 판정에 따라 야간 일정이 달라지기 때문입니다.

## 3. Drive 위의 checkpoint 구조

checkpoint는 먼저 런타임 로컬 디스크에 쓴 다음 검증하고, 그다음 Drive로 복사합니다. Drive에
직접 쓰면 쓰기가 느리고 중간에 끊겼을 때 손상된 파일이 남을 수 있기 때문입니다.

```
RUN_ROOT/<run_id>/
├─ run_manifest.json          모델, revision, 정밀도, 프롬프트, 해상도, 데이터 해시
├─ train_log.jsonl            step별 loss와 학습률
├─ heartbeat.json             프로세스가 살아 있는지 확인하는 기록
├─ checkpoints/
│  ├─ step_000123/
│  │  ├─ adapter/             LoRA 가중치
│  │  ├─ optimizer.pt
│  │  ├─ scheduler.pt
│  │  ├─ rng.pt
│  │  ├─ trainer_state.json
│  │  └─ COMPLETE             파일 해시를 담고 있으며 가장 마지막에 기록됩니다.
│  ├─ step_000246/
│  └─ latest.json             모든 것이 끝난 뒤 가장 마지막에 갱신됩니다.
├─ final_adapter/             학습이 끝난 adapter
│  └─ processor/              재현용 processor 사본. 학습 종료 시 한 번만 저장하며 추론은 읽지 않습니다.
└─ preds/                     예측 확률과 manifest
```

`RUN_ROOT` 는 환경 변수 `VQA_RUN_ROOT` 로 지정하며, 실습실에서는 `artifacts/runs` 가 기본값이고
Colab에서는 노트북이 `/content/drive/MyDrive/vqa/runs` 를 지정합니다. run 폴더와 같은 높이에
`preflight/<시각>.json` 과 `env_lock.txt`, `budget.json` 이 함께 쌓입니다. 앞의 것은
`python -m vqa.preflight` 가 남기는 점검 결과이고, 뒤의 두 개는
`20_colab_27b_setup_preflight.ipynb` 가 설치 버전과 예산 계산을 고정해 두는 파일입니다.

`COMPLETE` 표시가 없는 폴더는 저장이 끝나지 않은 것이므로 재개에 사용하지 않습니다.
`latest.json` 을 가장 마지막에 갱신하는 이유도 같습니다. 복사 도중에 세션이 끊기더라도
`latest.json` 은 여전히 직전의 완결된 checkpoint를 가리킵니다.

저장은 optimizer step 경계에서만 일어납니다. 설정한 step 간격이나 시간 간격에 도달할 때, 종료
신호를 받을 때, 학습이 끝날 때 저장합니다. 완결된 checkpoint는 최근 두 개만 남기고 나머지는
지웁니다. Drive 용량이 넉넉하지 않기 때문입니다.

## 4. 상황별 대응

### 셀을 실수로 중단했습니다

아무 문제도 생기지 않았습니다. 분리된 프로세스는 계속 돌아가고 있습니다. `jobs status` 셀로
확인한 다음 감시 셀만 실행하면 됩니다.

### 브라우저를 닫았다가 다시 들어왔습니다

`21_colab_27b_run.ipynb` 의 0번 절을 따릅니다. 파라미터 셀과 Drive 연결 셀, 부트스트랩 셀을
실행하고 `jobs status` 로 확인합니다. 프로세스가 살아 있으면 추가로 할 일이 없습니다.

### 가상 머신이 회수되었습니다

`/content` 아래의 데이터가 사라지고 job도 죽어 있습니다. 대응 순서는 다음과 같습니다.

1. 새 런타임에서 Drive를 다시 연결합니다.
2. 데이터 재준비 셀을 실행해서 압축 파일을 로컬 디스크에 다시 풉니다.
3. 가중치 캐시가 Drive에 있으면 그대로 쓰고, 로컬에 있었다면 다시 받습니다. 이 경우 수십 분이
   걸릴 수 있습니다.
4. 원래 실행했던 시작 셀을 그대로 다시 실행합니다. 명령을 고치지 않습니다. `--resume auto` 가
   기본이므로 Drive에 남은 checkpoint에서 이어집니다.

재개한 뒤에는 `train_log.jsonl` 에서 step이 이어지는지, loss가 급격히 튀지 않는지 확인합니다.
loss가 크게 튀면 optimizer 상태나 scheduler가 제대로 복원되지 않은 것이므로 그대로 두지 말고
확인해야 합니다.

### compute unit이 소진되었습니다

27B 경로를 더 진행할 수 없습니다. 이 상황은 예산 계산으로 미리 막아야 합니다. 그래도 발생했다면
실습실 9B 결과를 최종 후보로 쓰고, 이미 확보한 27B base 확률이 있으면 결합 후보로 씁니다.
새 계정을 만들거나 결제를 급하게 바꾸는 대응은 하지 않습니다.

### 적합한 GPU가 배정되지 않습니다

감지된 VRAM이 35GB 미만이면 `20_colab_27b_setup_preflight.ipynb` 의 config 선택 셀이 오류를
내면서 멈춥니다. 이때는 27B를 포기하고 실습실 9B 경로에 인력을 더 투입합니다. 27B를 CPU로
오프로드해서 학습하는 방법은 일정의 필수 경로로 삼지 않습니다.

### 학습은 살아 있는데 진행이 멈춘 것 같습니다

`heartbeat.json` 의 갱신 시각을 봅니다. 최근 갱신이 몇 분 이내라면 정상입니다. 갱신이 멈췄는데
프로세스는 살아 있다면 교착 상태일 수 있으므로, `jobs stop` 으로 중단하고 같은 시작 셀을 다시
실행합니다.

## 5. compute unit 예산

공식 요금 안내에서 Pro+는 월 600 CU로 소개됩니다. 다만 실제로 지급된 계정의 잔여량과 만료일,
GPU별 시간당 소모량은 계정 화면에서 직접 확인해야 합니다. Colab은 잔여 CU를 조회하는 API를
제공하지 않으므로, 노트북의 수동 입력 셀에 눈으로 본 값을 적습니다.

시간당 소모량을 모르면 30분 정도 실행한 뒤 줄어든 양을 보고 역산합니다. 계산용 가정값인 7.5 CU/h
같은 숫자는 실제 계획에 그대로 쓰지 않습니다.

예산은 다음 다섯 항목을 모두 더해서 계산합니다.

1. base validation 추론에 드는 시간
2. base 전체 test 추론에 드는 시간
3. 학습 1 epoch에 드는 시간
4. 미세조정 후 validation 추론에 드는 시간
5. 미세조정 후 전체 test 추론에 드는 시간

여기에 20퍼센트를 복구와 최종 추론 예비분으로 더합니다. 이 합계가 잔여 CU의 80퍼센트 안에
들어와야 27B 경로를 유지할 수 있습니다. `20_colab_27b_setup_preflight.ipynb` 의 마지막 셀이 이
계산을 실측값으로 수행하고, 초과하면 경고를 출력합니다.

예산을 초과하면 실행을 시작하기 전에 예외를 적용할지 결정합니다. 실습실 9B의 전체 base 결과를
조기 제출로 사용하고, 27B는 validation과 미세조정 후 전체 추론만 담당하도록 줄이는 방식입니다.
이 결정은 실행 도중에 내리지 않습니다. 중간까지만 끝난 base 결과를 전체 안전망으로 착각하면
마감 직전에 제출할 파일이 없는 상황이 생깁니다.

시간을 계산할 때는 준비와 warm-up 시간을 측정에서 분리합니다. 첫 실행에는 모델 로딩과 컴파일에
시간이 걸리므로, 그 값을 문항당 시간에 포함하면 전체 예상이 크게 부풀려집니다. preflight가 cold
실행과 warm 실행을 나눠서 보고하므로 두 숫자를 모두 기록하십시오.

학습 시간을 환산할 때에는 preflight가 보고하는 `sec_per_optimizer_step` 을 씁니다. 이 값은
`sec_per_microbatch_mean` 에 `grad_accum` 을 곱한 값이며, 누적이 8이면 20 optimizer step은 최대
160 microbatch에 해당합니다. microbatch 값으로 계산하면 학습 시간을 누적 배수만큼 낮게 잡게
됩니다. 옛 이름인 `warm_seconds_mean` 은 `sec_per_microbatch_mean` 의 별칭이므로 예산 계산에
쓰지 마십시오. 참고로 `sec_per_microbatch_longest` 는 가장 긴 표본이며, 여유분을 잡을 때 평균과
얼마나 벌어지는지를 보는 용도입니다.
