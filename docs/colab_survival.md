# Colab 세션 생존 설계

담당은 준혁입니다. Colab 런타임을 조작하는 사람은 한 명으로 유지합니다. 다른 팀원은 노트북을
열어 볼 수는 있지만 실행 중인 가상 머신은 공유되지 않으므로, 진행 상황은 Drive에 저장된 로그로만
확인합니다.

이 문서는 세션이 끊기는 상황을 전제로 실행을 설계하는 방법을 설명합니다. 끊기지 않게 만드는 것이
아니라, 끊기더라도 손실이 몇 분치에 그치도록 만드는 것이 목표입니다.

## 0. 노트북 하나가 가상 머신 하나입니다

Colab은 노트북마다 가상 머신을 하나씩 따로 배정합니다. 그래서 20번 노트북에서 설치한 패키지는
21번 노트북의 가상 머신에 하나도 남아 있지 않습니다. 2026-09-21에 27B 작업이
`Using bitsandbytes 4-bit quantization requires bitsandbytes` 오류로 세 번 죽은 원인이 바로
이것입니다. 작업을 시작하기 전에 런타임 메뉴의 세션 관리 화면에서 다른 노트북의 세션을 반드시
종료하십시오. A100 두 대가 동시에 돌면 compute unit이 두 배로 빠지고, 80GB를 배정받을 확률도
떨어집니다. 새 가상 머신을 받은 다음에는 21번 노트북의 파라미터 셀부터 데이터 준비 셀까지를
빠짐없이 실행한 뒤에 job을 시작하십시오.

Colab 기본 이미지에는 torchao 0.10.0이 들어 있습니다. PEFT가 비양자화 Linear에 LoRA를 붙일 때
`Found an incompatible version of torchao ... only versions above 0.16.0 are supported` 로
실패하므로, bf16 경로에서는 설치 전에 `pip uninstall -y torchao` 를 먼저 실행해야 합니다.
20번과 21번 노트북의 환경 설치 셀이 이 순서를 그대로 수행하고, 별도 프로세스에서 다시 import
해서 버전과 GPU를 확인합니다. 커널이 이미 읽어 둔 모듈 때문에 옛 버전이 그대로 보이는 일을
막기 위해서입니다.

## 0-1. 가속 커널을 반드시 설치합니다

transformers의 Qwen3.5 Gated DeltaNet은 `fla` 패키지가 있으면 그 전용 커널을 쓰고, 없으면
PyTorch 참조 구현으로 내려갑니다. 내려갈 때에는 다음과 같은 경고를 남깁니다.

```
`chunk_gated_delta_rule` is falling back to its reference PyTorch implementation
because ... is not installed
```

2026-09-21 Colab A100에서 bf16 학습이 optimizer step당 58초, microbatch당 7.3초로 나왔습니다.
같은 모델을 같은 해상도로 돌린 참고 실행은 microbatch당 3.37초였으므로 두 배 이상 느렸던
셈이고, 그 원인이 이 fallback이었습니다. 열 시간이면 끝날 학습이 스무 시간으로 늘어나므로
compute unit 예산에도 그대로 영향을 줍니다.

설치 명령은 다음 두 줄입니다. 반드시 `--no-deps` 를 붙여야 합니다. 그렇게 하지 않으면 fla가
자기 의존성으로 torch와 triton을 다시 끌어와서, 이미 통과해 둔 torch 빌드가 바뀝니다.

```
pip install --no-deps fla-core flash-linear-attention
pip install einops
```

저장소에서는 `requirements/colab-nodeps.txt` 가 앞의 두 패키지를, `requirements/colab.txt` 가
einops를 담당합니다. 20번과 21번 노트북의 환경 설치 셀이 이 순서를 그대로 수행한 다음, 설치
전후의 torch 버전이 같은지 확인하고, 별도 프로세스에서 작은 텐서 하나로 커널의 forward와
backward가 유한한 값을 내는지까지 확인합니다. 이 단계가 실패하더라도 학습 자체는 가능하므로
셀은 멈추지 않고 경고만 크게 출력합니다. `python -m vqa.preflight` 의 `kernel_fast_path`
검사도 같은 내용을 WARN으로 알려 줍니다. WARN은 종료 코드를 바꾸지 않습니다.

causal-conv1d는 선택 사항입니다. wheel이 없어서 소스 빌드가 필요하고, 이 패키지가 없을 때
생기는 fallback은 Gated DeltaNet 경로가 아니라 short convolution 경로여서 속도에 주는 영향이
훨씬 작습니다. preflight도 이 경우는 정보로만 남기고 WARN으로 올리지 않습니다.

## 0-2. GPU 작업은 한 번에 하나만 돌립니다

2026-09-21에 21번 노트북의 GPU 셀 네 개를 연달아 실행해서 모델 네 개가 동시에 올라갔고, 그
결과로 out of memory가 났습니다. `python -m vqa.jobs start` 는 job을 띄우자마자 곧바로
돌아오기 때문에, 셀이 끝났다는 사실이 작업이 끝났다는 뜻은 아닙니다.

지금은 다음 세 가지가 이 상황을 막습니다.

1. `vqa.jobs start` 는 같은 run-root에 살아 있는 job이 있으면 시작을 거부합니다. 의도적으로
   동시에 돌려야 하면 `--allow-concurrent` 를 붙입니다.
2. `vqa.jobs start --min-free-gb N` 은 GPU 여유 메모리가 N GB에 못 미치면 시작을 거부합니다.
3. `python -m vqa.jobs wait --name <이름> --poll 30` 은 job이 끝날 때까지 기다립니다. 종료
   코드는 정상 종료가 0, 실패가 1, 제한 시간 초과가 2입니다. 21번 노트북의 GPU 단계는 job을
   띄운 다음 이 명령으로 기다리므로, 메뉴의 "모두 실행"을 눌러도 작업이 겹치지 않습니다.

예외는 학습 하나뿐입니다. 학습은 열 시간 안팎이 걸려서 셀을 그만큼 붙잡아 둘 수 없으므로 띄우기만
하고 기다리지 않습니다. 그래서 학습 다음에 오는 셀들은 실행하기 전에 학습 job이 아직 살아 있는지와
`final_adapter` 가 만들어졌는지를 스스로 확인하고, 아직 때가 아니면 안내만 출력한 다음 아무 일도
하지 않고 끝납니다. 혹시 그 확인을 지나쳐서 job을 띄우려 하더라도 1번 규칙이 다시 한 번 막아 줍니다.

preflight는 `python -m vqa.preflight` 를 직접 실행하면 이 가드가 보지 못하는 자리에서 모델을
올리게 됩니다. 2026-09-21에 preflight가 학습과 겹쳐서 out of memory가 났던 원인이 바로 그것입니다.
그래서 21번 노트북은 preflight도 `vqa.jobs start` 로 띄우고 `vqa.jobs wait` 로 기다립니다. 다른
job이 살아 있으면 preflight 역시 시작이 거부됩니다.

## 1. 무엇이 살아남고 무엇이 죽는지

정확히 구분해야 밤샘 실행을 맡길지 판단할 수 있습니다. 오래 걸리는 작업은 모두
`python -m vqa.jobs start` 로 부모 프로세스에서 분리해서 띄웁니다.

분리된 프로세스가 살아남는 상황은 다음과 같습니다.

- 노트북 셀을 중단했을 때에도 계속 실행됩니다.
- 브라우저 탭을 닫았을 때에도 계속 실행됩니다.
- 노트북 화면과 런타임 사이의 연결이 일시적으로 끊겼을 때에도 계속 실행됩니다.

분리된 프로세스도 함께 죽는 상황은 다음과 같습니다.

- 유휴 시간 초과로 런타임이 회수되면 함께 종료됩니다.
- 최대 연속 실행 시간에 도달하면 함께 종료됩니다.
- compute unit이 소진되면 함께 종료됩니다.
- 자원 사정으로 인스턴스가 선점되면 함께 종료됩니다.
- 사용자가 런타임을 직접 종료하거나 다시 시작하면 함께 종료됩니다.

Pro+ 구독은 백그라운드 실행을 제공한다고 안내되어 있습니다. 다만 실제 계정과 실제 런타임에서
어떻게 동작하는지는 안내 문구만으로 확정할 수 없으므로, D1에 직접 확인해야 합니다. 확인 절차는
아래 2절에 있습니다.

세션을 유지하겠다고 자동 클릭 스크립트나 가짜 입력을 만드는 방법은 사용하지 않습니다. Colab
이용 약관에 어긋나고, 계정이 제한되면 팀 전체의 GPU 경로가 사라집니다. 대신 checkpoint를 Drive에
자주 남겨서 언제 끊기더라도 이어서 실행할 수 있게 만드는 방식으로 대응합니다.

## 2. 백그라운드 실행 확인 절차

D1에 한 번만 수행합니다. `21_colab_27b_run.ipynb` 의 부록 A에 이 절차를 실행하는 셀이 있습니다.
본 실행 흐름과 분리해 두었으므로, 필요할 때에만 그 두 셀을 실행하면 됩니다.

1. 시험용 job을 띄웁니다. 이 job은 15분 동안 1분마다 Drive의 파일에 현재 시각을 기록합니다.
2. 브라우저 탭을 완전히 닫습니다. 창을 최소화하거나 다른 탭으로 옮기는 것이 아니라 탭 자체를
   닫아야 합니다.
3. 10분 정도 지난 뒤에 다시 접속합니다.
4. 확인 셀을 실행해서 기록된 시각 사이에 빈 구간이 있는지 봅니다.

판정 기준은 다음과 같습니다. 기록이 1분 간격으로 끊김 없이 이어지면, 탭을 닫아도 실행이 유지되는
것이므로 야간 실행을 맡길 수 있습니다. 탭을 닫은 시점부터 기록이 멈췄다가 다시 접속한 시점부터
재개되었다면, 백그라운드 실행이 동작하지 않는 것입니다. 이 경우에는 탭을 열어 둔 채로 실행하고,
checkpoint 저장 간격을 짧게 잡아야 합니다.

확인 결과는 팀 채널에 반드시 공유합니다. 이 판정에 따라 야간 일정이 달라지기 때문입니다.

## 3. 코드 가져오기

새로 만들어진 Colab 가상 머신에는 저장소가 들어 있지 않습니다. 부트스트랩 셀이 `PROJECT_ROOT` 로
작업 디렉터리를 옮기기 때문에, 그보다 앞에서 코드를 먼저 내려받아야 합니다. 두 노트북 모두 Drive
연결 셀 바로 다음에 코드 가져오기 셀을 두었습니다.

이 저장소는 비공개이므로 인증 수단이 필요합니다. 기본 방법은 토큰을 쓰는 것입니다.

1. GitHub의 Settings에서 Developer settings로 들어가 fine-grained personal access token을
   만듭니다. 대상 저장소를 이 저장소 하나로 좁히고, 권한은 Contents 읽기 전용으로만 줍니다.
2. Colab 화면 왼쪽의 열쇠 아이콘 패널을 엽니다. 새 비밀을 추가하고 이름을 `GITHUB_TOKEN` 으로
   적은 다음 토큰 값을 붙여 넣습니다.
3. 같은 줄의 노트북 액세스 스위치를 켜야 노트북에서 그 값을 읽을 수 있습니다.

셀은 토큰을 화면이나 로그에 출력하지 않습니다. 복제에 쓴 주소에 토큰이 들어가기 때문에, 복제가
끝나는 즉시 `git remote set-url` 로 원래 주소를 다시 설정해서 `.git/config` 에 토큰이 남지 않게
합니다. 오류 문구에도 토큰이 섞이지 않도록 출력을 걸러서 보여 줍니다.

토큰을 쓸 수 없는 상황이라면 코드 전체를 zip으로 묶어 Drive에 올리고, 파라미터 셀의 `CODE_ZIP` 에
그 경로를 적습니다. 압축 안에 최상위 폴더가 하나만 있어도 그 내용을 펼쳐서 `PROJECT_ROOT` 바로
아래에 놓습니다.

코드가 이미 받아져 있으면 `git pull --ff-only` 로 갱신만 하고, 갱신이 실패하더라도 멈추지 않고
기존 코드를 그대로 사용합니다. 돌고 있는 job은 이미 읽어 들인 코드로 계속 실행되므로 갱신의
영향을 받지 않습니다. 다만 코드나 config가 바뀐 뒤에 job을 다시 띄우면 `--resume auto` 가 config
해시 불일치를 이유로 재개를 거부할 수 있습니다. 그러므로 코드 갱신은 실행 중인 작업이 없는
사이에만 하십시오.

## 4. Drive 위의 checkpoint 구조

checkpoint는 먼저 런타임 로컬 디스크에 쓴 다음 검증하고, 그다음 Drive로 복사합니다. Drive에
직접 쓰면 쓰기가 느리고 중간에 끊겼을 때 손상된 파일이 남을 수 있기 때문입니다.

```
RUN_ROOT/<run_id>/
├─ run_manifest.json          모델, revision, 정밀도, 프롬프트, 해상도, 데이터 해시
├─ train_log.jsonl            step별 loss와 학습률
├─ heartbeat.json             프로세스가 살아 있는지 확인하는 기록
├─ checkpoints/
│  ├─ step_000123/
│  │  ├─ adapter/             LoRA 가중치
│  │  ├─ optimizer.pt
│  │  ├─ scheduler.pt
│  │  ├─ rng.pt
│  │  ├─ trainer_state.json
│  │  └─ COMPLETE             파일 해시를 담고 있으며 가장 마지막에 기록됩니다.
│  ├─ step_000246/
│  └─ latest.json             모든 것이 끝난 뒤 가장 마지막에 갱신됩니다.
├─ final_adapter/             학습이 끝난 adapter
│  └─ processor/              재현용 processor 사본. 학습 종료 시 한 번만 저장하며 추론은 읽지 않습니다.
└─ preds/                     예측 확률과 manifest
```

`RUN_ROOT` 는 환경 변수 `VQA_RUN_ROOT` 로 지정하며, 실습실에서는 `artifacts/runs` 가 기본값이고
Colab에서는 노트북이 `/content/drive/MyDrive/vqa/runs` 를 지정합니다. run 폴더와 같은 높이에
`preflight/<시각>.json` 과 `env_lock.txt`, `budget.json` 이 함께 쌓입니다. 앞의 것은
`python -m vqa.preflight` 가 남기는 점검 결과이고, 뒤의 두 개는
`20_colab_27b_setup_preflight.ipynb` 가 설치 버전과 예산 계산을 고정해 두는 파일입니다.

같은 높이에 노트북이 남기는 기록 파일이 세 개 더 있습니다. `code_version.txt` 에는 실행할 때마다
시각과 코드 commit 해시가 한 줄씩 덧붙습니다. 나중에 어떤 코드로 돌린 결과인지 추적하는 데
씁니다. `colab_choice.json` 에는 20번 노트북이 VRAM을 보고 고른 config와 정밀도가 들어
있습니다. 21번 노트북은 이 파일을 참고 정보로만 출력하고 자기 선택을 덮어쓰지 않습니다. 20번이
40GB에서 고른 nf4가 80GB 가상 머신까지 따라와서 조용히 nf4로 돌아간 사고가 있었기 때문입니다.
정밀도는 21번이 그때그때 직접 잰 VRAM으로 정하며, 파라미터 셀에 `CONFIG` 를 적었다면 그 값이
무엇보다 우선합니다. `model_snapshot.json` 에는 모델 식별자와 revision, 가중치 캐시 위치가 들어
있습니다. 21번 노트북은 이 파일의 캐시 위치가 현재 런타임에 실제로 있으면 그대로 쓰고, 없으면
`/content/hf_cache` 로 내려가면서 가중치를 다시 받게 된다는 사실을 함께 출력합니다.

`COMPLETE` 표시가 없는 폴더는 저장이 끝나지 않은 것이므로 재개에 사용하지 않습니다.
`latest.json` 을 가장 마지막에 갱신하는 이유도 같습니다. 복사 도중에 세션이 끊기더라도
`latest.json` 은 여전히 직전의 완결된 checkpoint를 가리킵니다.

저장은 optimizer step 경계에서만 일어납니다. 설정한 step 간격이나 시간 간격에 도달할 때, 종료
신호를 받을 때, 학습이 끝날 때 저장합니다. 완결된 checkpoint는 최근 두 개만 남기고 나머지는
지웁니다. Drive 용량이 넉넉하지 않기 때문입니다.

## 5. 상황별 대응

### 셀을 실수로 중단했습니다

아무 문제도 생기지 않았습니다. 분리된 프로세스는 계속 돌아가고 있습니다. 21번 노트북의 상태
확인 셀로 살아 있는지 확인한 다음, 기다리던 셀을 다시 실행하면 됩니다. 기다리는 셀은
`vqa.jobs wait` 를 다시 호출할 뿐이므로 job에는 아무 영향도 주지 않습니다.

### 브라우저를 닫았다가 다시 들어왔습니다

`21_colab_27b_run.ipynb` 의 맨 위에 있는 재시작 안내를 따릅니다. 파라미터 셀과 Drive 연결 셀,
코드 가져오기 셀과 부트스트랩 셀, 환경 설치와 확인 셀, GPU와 정밀도 결정 셀, 데이터 준비 셀,
실행 도우미 셀을 차례로 실행한 다음, 중단된 지점의 셀을 그대로 다시 실행하면 됩니다. 프로세스가 아직 살아 있으면
기다리는 셀이 그대로 이어서 기다립니다.

### 가상 머신이 회수되었습니다

`/content` 아래의 데이터가 사라지고 job도 죽어 있습니다. 대응 순서는 다음과 같습니다.

1. 새 런타임에서 Drive를 다시 연결합니다.
2. 코드 가져오기 셀을 실행해서 저장소를 다시 내려받습니다. `/content` 가 비워졌으므로 코드도
   함께 사라진 상태입니다.
3. 데이터 재준비 셀을 실행해서 압축 파일을 로컬 디스크에 다시 풉니다.
4. 가중치 캐시가 Drive에 있으면 그대로 쓰고, 로컬에 있었다면 다시 받습니다. 이 경우 수십 분이
   걸릴 수 있습니다.
5. 원래 실행했던 시작 셀을 그대로 다시 실행합니다. 명령을 고치지 않습니다. `--resume auto` 가
   기본이므로 Drive에 남은 checkpoint에서 이어집니다.

재개한 뒤에는 `train_log.jsonl` 에서 step이 이어지는지, loss가 급격히 튀지 않는지 확인합니다.
loss가 크게 튀면 optimizer 상태나 scheduler가 제대로 복원되지 않은 것이므로 그대로 두지 말고
확인해야 합니다.

### compute unit이 소진되었습니다

27B 경로를 더 진행할 수 없습니다. 이 상황은 예산 계산으로 미리 막아야 합니다. 그래도 발생했다면
실습실 9B 결과를 최종 후보로 쓰고, 이미 확보한 27B base 확률이 있으면 결합 후보로 씁니다.
새 계정을 만들거나 결제를 급하게 바꾸는 대응은 하지 않습니다.

### 적합한 GPU가 배정되지 않습니다

감지된 VRAM이 35GB 미만이면 `20_colab_27b_setup_preflight.ipynb` 의 config 선택 셀이 오류를
내면서 멈춥니다. 이때는 27B를 포기하고 실습실 9B 경로에 인력을 더 투입합니다. 27B를 CPU로
오프로드해서 학습하는 방법은 일정의 필수 경로로 삼지 않습니다.

### 학습은 살아 있는데 진행이 멈춘 것 같습니다

`heartbeat.json` 의 갱신 시각을 봅니다. 최근 갱신이 몇 분 이내라면 정상입니다. 갱신이 멈췄는데
프로세스는 살아 있다면 교착 상태일 수 있으므로, `python -m vqa.jobs stop --name <이름>` 으로
중단하고 같은 시작 셀을 다시 실행합니다. 이 명령은 실제 학습 프로세스에 SIGTERM을 전달하고,
학습은 그 신호를 받아 step 경계에서 checkpoint를 저장한 다음 종료합니다. 그러므로 중단해도
잃는 것은 마지막 step 하나뿐입니다.

## 6. compute unit 예산

공식 요금 안내에서 Pro+는 월 600 CU로 소개됩니다. 다만 실제로 지급된 계정의 잔여량과 만료일,
GPU별 시간당 소모량은 계정 화면에서 직접 확인해야 합니다. Colab은 잔여 CU를 조회하는 API를
제공하지 않으므로, 노트북의 수동 입력 셀에 눈으로 본 값을 적습니다.

시간당 소모량을 모르면 30분 정도 실행한 뒤 줄어든 양을 보고 역산합니다. 계산용 가정값인 7.5 CU/h
같은 숫자는 실제 계획에 그대로 쓰지 않습니다.

예산은 다음 다섯 항목을 모두 더해서 계산합니다.

1. base validation 추론에 드는 시간
2. base 전체 test 추론에 드는 시간
3. 학습 1 epoch에 드는 시간
4. 미세조정 후 validation 추론에 드는 시간
5. 미세조정 후 전체 test 추론에 드는 시간

여기에 20퍼센트를 복구와 최종 추론 예비분으로 더합니다. 이 합계가 잔여 CU의 80퍼센트 안에
들어와야 27B 경로를 유지할 수 있습니다. `20_colab_27b_setup_preflight.ipynb` 의 마지막 셀이 이
계산을 실측값으로 수행하고, 초과하면 경고를 출력합니다.

예산을 초과하면 실행을 시작하기 전에 예외를 적용할지 결정합니다. 실습실 9B의 전체 base 결과를
조기 제출로 사용하고, 27B는 validation과 미세조정 후 전체 추론만 담당하도록 줄이는 방식입니다.
이 결정은 실행 도중에 내리지 않습니다. 중간까지만 끝난 base 결과를 전체 안전망으로 착각하면
마감 직전에 제출할 파일이 없는 상황이 생깁니다.

시간을 계산할 때는 준비와 warm-up 시간을 측정에서 분리합니다. 첫 실행에는 모델 로딩과 컴파일에
시간이 걸리므로, 그 값을 문항당 시간에 포함하면 전체 예상이 크게 부풀려집니다. preflight가 cold
실행과 warm 실행을 나눠서 보고하므로 두 숫자를 모두 기록하십시오.

학습 시간을 환산할 때에는 preflight가 보고하는 `sec_per_optimizer_step` 을 씁니다. 이 값은
`sec_per_microbatch_mean` 에 `grad_accum` 을 곱한 값이며, 누적이 8이면 20 optimizer step은 최대
160 microbatch에 해당합니다. microbatch 값으로 계산하면 학습 시간을 누적 배수만큼 낮게 잡게
됩니다. 옛 이름인 `warm_seconds_mean` 은 `sec_per_microbatch_mean` 의 별칭이므로 예산 계산에
쓰지 마십시오. 참고로 `sec_per_microbatch_longest` 는 가장 긴 표본이며, 여유분을 잡을 때 평균과
얼마나 벌어지는지를 보는 용도입니다.
