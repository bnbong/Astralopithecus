# 텍스트 이미지 기반 질의응답(VQA) 챌린지 제출 보고서 (축약본)

이 문서는 대회 제출 요건 가운데 "데이터 처리 및 모델 개발 과정에 대한 설명 문서"에 해당합니다. 본문의 수치와 경로는 모두 저장소 안의 기록에서 읽어 온 값이며, 내부 기록을
모두 담은 상세본은 `docs/submission_report.md`에 따로 보관해 두었습니다.

---

## 1. 개요

### 1.1 팀 구성

팀 이름은 Astralopithecus이며 구성원은 다섯 명입니다.

| 팀원 | 역할 |
|---|---|
| 준혁 | 전체 통합과 Colab A100에서의 27B 실행을 맡았습니다. |
| 수빈 | 데이터 감사와 공식 분할 확정, 오답 라벨 점검을 맡았습니다. |
| 유림 | 공통 학습 코드(`vqa/` 패키지)와 실습실 PC에서의 9B 학습을 맡았습니다. |
| 창혁 | 프롬프트 비교, 외부 OCR 검토, 입력 해상도 결정을 맡았습니다. |
| 수정 | 평가와 확률 결합, 제출 파일 검사를 맡았습니다. |

서로 기다리는 시간을 줄이기 위해 각자의 산출물을 파일로 먼저 정의했고, 예측 확률 파일의 컬럼을 `id,p_a,p_b,p_c,p_d,run_id` 순서로 미리 고정해서 누가 만든
파일이든 같은 스크립트에 넣을 수 있게 했습니다.

### 1.2 과제

이 과제는 이미지 한 장과 한국어 질문 하나, 그리고 a부터 d까지 네 개의 선택지를 입력으로 받아서 정답 선택지 하나를 고르는 4지선다 VQA 문제이며 평가 지표는 정확도입니다.
학습 데이터가 6,714문항이고 평가 데이터도 6,714문항이며, 보조 데이터인 `dev.csv`는 2,683행으로 교육생 다섯 명의 응답을 담고 있습니다.

이 데이터의 가장 큰 특징은 이미지 안에 적힌 글자를 읽어야 풀리는 문항이 많다는 점입니다. 검증에 사용한 fold 0 1,344문항을 유형별로 나누면 숫자를 포함한 문항이 539개,
선택지가 한국어인 문항이 602개, 대부분 영문으로 적힌 문항이 152개, 전화번호 형태의 문항이 34개, 그 밖이 17개입니다. 무작위로 골라도 25퍼센트는 맞는 과제라서 의미 있는
차이가 90퍼센트대 후반에서 갈리므로, 저희는 처음부터 글자를 정확히 읽어 내는 능력을 기준으로 삼았습니다.

### 1.3 최종 결과와 제출물

최종 제출물은 두 개이며, 1순위의 Public 점수는 0.97765입니다.

| 순위 | 후보 | 구성 | Public | 제출 파일 sha256 |
|---|---|---|---|---|
| 1순위 | ⑳ | A 0.3 + B 0.3 + Gemma QLoRA 0.4의 확률 가중 평균 결합 | 0.97765 | `31f51fe5c1cd0523f5f7c7fac12fa33398b34b4976aa66b62fa4ea343e101841` |
| 2순위 | ⑲ | A 0.3 + B 0.3 + Gemma zero-shot 0.4의 확률 가중 평균 결합 | 0.97616 | `e6a9d531b467ac8f17be7a9b33bc65b6ef0090b8a2006e4d5b808a03b0fa15fd` |

두 제출물은 가중치가 똑같고 세 번째 재료로 Gemma의 QLoRA 학습 모델을 쓰는지 zero-shot 모델을 쓰는지만 다릅니다. 공통 재료인 A와 B는 모두 Qwen3.5-27B를
bf16으로 올리고 프롬프트 `v2_read_text`와 이미지 확대 설정으로 answer-only LoRA를 학습한 모델입니다. 2순위를 Public 점수가 더 높은
㉓(0.97676)이 아니라 ⑲로 둔 까닭은, 2순위가 1순위를 대비하는 보험 자리이므로 1순위와 예측이 가장 많이 다른 제출물을 두는 편이 낫다고 보았기 때문입니다. ⑲는 ⑳과 답이
갈린 문항이 43개인 반면 ㉓은 28개에 그칩니다.

### 1.4 핵심 결론 세 가지

첫째로 이 과제에서 얻은 이득은 모델 크기가 가장 컸고 그다음이 입력 해상도였으며 LoRA 학습은 그보다 작았습니다. 둘째로 같은 계열(Qwen3.5-27B) 안에서 배깅과 dev
세트 추가, epoch 연장, seed 변경, 전체 데이터 재학습을 아무리 얹어도 점수가 움직이지 않았습니다. 셋째로 점수를 실제로 끌어올린 조작은 시각 인코더 계열이 다른
Gemma-4-31B-it를 결합에 넣은 일 하나뿐이었고, 그 계열 다양성도 단독 강도가 A 수준에 닿아야만 이득이 났습니다.

## 2. 데이터 처리

### 2.1 데이터 구성과 감사

`scripts/audit_data.py`로 세 분할의 CSV와 이미지 폴더를 한 번에 점검했습니다. train 6,714행과 test 6,714행에는 빈 셀과 누락 이미지, 중복
id가 모두 0건이었고 모든 이미지가 Pillow로 정상적으로 열렸습니다. train의 정답 분포는 a가 1,700건, b가 1,644건, c가 1,716건, d가 1,654건으로
고르게 퍼져 있었습니다. 이미지 크기는 가로 중앙값이 720픽셀, 세로 중앙값이 960픽셀이며 화소 수 중앙값이 0.69메가픽셀인데, 짧은 변이 720픽셀인 세로 사진이 다수를
차지한다는 사실이 이미지 확대 결정의 근거가 되었습니다. 외부 데이터와 의사 라벨은 전혀 사용하지 않았고, 학습에 쓴 이미지와 라벨은 모두 주최 측이 제공한 train 데이터에서
나왔습니다.

### 2.2 고정 fold 분할

공식 검증셋은 train의 fold 0이며 1,344문항입니다. 분할 방식은 이미지 바이트의 MD5 해시를 그룹 키로 삼는
`sklearn.model_selection.StratifiedGroupKFold` 5-fold이고, `answer`로 stratify하며 `shuffle=True`와
`random_state=42`로 고정했습니다. 파일명만으로는 중복이 없지만 해시 기준으로는 train 내부에 동일한 이미지가 일곱 쌍 존재하므로, 파일명으로 무작위 분할하면 검증
점수가 부풀려집니다. 같은 이미지가 두 개 이상의 fold에 걸친 경우와 fold 0의 이미지 해시가 fold 1~4와 교차하는 경우는 모두 0건임을 확인했습니다.

| 분할 파일 | 문항 수 | 내용 해시 |
|---|---|---|
| `artifacts/data/split_fold0.json` | 학습 5,358, 검증 1,344 | `ea2c8572129342f138c551e6e32a3427902c730db349c45d0e5342f03dfccae0` |
| `artifacts/data/split_full.json` | 6,690 | `ecffa479fd5764376d32af9420c5f0015a8bb76f657c976617e357ce69989af9` |

팀원 모두가 같은 데이터로 평가하고 있는지를 `split_fold0.json`의 내용 해시 하나로 확인했습니다. `split_full.json`의 6,690문항은 train
6,714문항에서 test와 완전 중복인 24건을 뺀 수입니다. 주최 측이 제공한 데이터이므로 사용 자체는 문제가 없을 가능성이 높지만, test 이미지와 직접 연결된 정보를 학습하는
일은 오해의 소지가 있고 제외해도 손실이 0.36퍼센트에 불과했기 때문에 빼는 쪽을 선택했습니다.

### 2.3 dev 세트 활용과 기각

dev는 보조 참고용으로만 쓰기로 정했습니다. 다섯 명의 응답 가운데 네 표 이상이 일치한 문항이 한 건도 없었고, 최다 득표 합의율의 중앙값이 60퍼센트에 그쳤으며, 동률인 문항이
465건(17.3퍼센트)이었기 때문입니다. 동률이 없고 세 표가 합의하면서 train과 겹치지 않는 2,024문항만 `fold_csv_files/dev_aux.csv`로 추렸고, 그
가운데 test와 이미지가 겹치는 4건을 제외한 2,020문항을 A 설정의 학습 데이터에 추가해 다시 학습해 보았습니다. 학습 데이터를 38퍼센트 늘렸는데도 fold 0 정확도는
0.9695(1303/1344)로 A의 0.9688(1302/1344)보다 1문항 늘어나는 데 그쳤고 McNemar 검정의 p값이 1.0이었으므로 기각했습니다. 결합 재료로서의
가능성도 test 제출로 확인했지만 Public 0.96931과 0.96991에 머물러 함께 기각했습니다.

### 2.4 라벨 점검

fold 0에서 남은 오답이 모델의 한계인지 라벨의 한계인지를 먼저 가르기 위해, 27B 학습 모델이 틀린 56문항을 두 사람이 독립적으로 전수 점검했습니다. 판정을 합친 결과는 라벨
문제가 35건, 작은 글자 때문에 생긴 모델 오류가 12건, 추론이 틀린 모델 오류가 8건, 미점검이 1건이었고, 라벨 문제 35건은 fold 0 1,344문항의 2.60퍼센트입니다.
모델 오류 20건과 미점검 1건을 모두 되돌린다고 가정하면 추정 상한이 (1288 + 21) / 1344 = 0.9740이며, 저희는 이 값을 더 올릴 여지가 거의 없는 지점을 알려
주는 참고선으로만 사용했습니다.

### 2.5 입력과 증강

학습 방식은 answer-only LoRA입니다. 정답 letter 토큰 한 개에만 loss를 걸고 system 프롬프트와 이미지, 질문, 선택지, assistant turn의 나머지
위치는 모두 `-100`으로 가립니다. 선지 하나를 고르는 과제에서 문장 전체를 학습시킬 이유가 없다고 보았기 때문이며, `vqa/collator.py`가 표본마다 정확히 한 개의
위치만 감독되는지를 매번 확인합니다. 프롬프트는 이미지에 적힌 글자를 먼저 정확히 읽으라고 지시하는 `v2_read_text`(p2)를 채택했고, 학습과 추론에 같은 값을 넘깁니다.

이미지 전처리는 Qwen processor의 `min_pixels`와 `max_pixels` 두 값으로만 제어했으며, 확대 설정은 `min_pixels`가 1,048,576이고
`max_pixels`가 2,097,152입니다. 상한이 아니라 하한을 올린 데에는 실측 근거가 있습니다. 작은 글자 때문에 틀렸다고 판정한 12문항의 원본 크기를 재 보니 모두 기존
상한인 1,048,576화소 아래에 있었으므로 상한을 올려도 입력이 전혀 바뀌지 않는 반면, 하한을 1,048,576으로 올리면 691,200화소짜리 이미지의 시각 토큰이 675개에서
1,024개로 늘어납니다. 상한을 2,097,152로 함께 올린 까닭은 확대한 이미지가 상한에 걸려서 다시 잘리는 일을 막기 위해서입니다.

이미지 증강은 사용하지 않았습니다. 글자를 읽어야 풀리는 문항이 많아서 회전이나 색 변환이 오히려 가독성을 떨어뜨릴 위험이 있다고 판단했기 때문입니다. 다만 학습에는 선택지 순열을
적용했습니다. 설정의 `train.shuffle_options`를 `true`로 두어 학습 표본마다 순서를 섞었으며, 모델이 선택지 위치를 외우지 못하게 하려는 처리입니다.

### 3.2 결합이 효과를 낸 조건

결합의 이득은 두 모델의 강도가 비슷하면서 서로 다른 자리에서 틀릴 때에만 나타났습니다. ⑩에서 A와 B는 설정이 모두 같고 학습 데이터만 5,358문항과 6,690문항으로 달랐는데,
test 6,714문항 가운데 답이 갈린 문항이 92개였고 확률 평균이 더 나은 쪽을 골라 주면서 점수가 올랐습니다. 반대로 절대 성능이 크게 차이 나는 9B를 섞은 ④는 Public
0.96425로 단독 모델보다 낮아졌습니다. 같은 계열 안에서 다양성을 늘리려던 시도도 모두 실패했습니다. 5-fold 배깅은 OOF 정확도가 6,510/6,714 = 0.9696이고
B와 2대 1로 섞은 값이 Public 0.97021에 그쳤으며, 3-epoch 학습은 세 epoch 모두 A에 미치지 못한 채로 오답의 평균 margin만 0.54에서 0.87로
커졌습니다. Gemma-4-31B-it를 섞고 나서야 ⑩을 넘었는데, fold 0에서 A만 맞힌 문항이 19개, Gemma만 맞힌 문항이 20개, 둘 다 틀린 문항이 22개여서
보완성이 충분했기 때문입니다. 다만 Gemma는 오답 margin이 평균 0.904에 이르는 과신 모델이어서, 가중치를 절반 아래로 낮추어야 했습니다.

### 3.3 검증 방법

모든 설정 비교는 고정된 fold 0 1,344문항에서만 수행했고 test로는 어떤 조정도 하지 않았습니다. 1,344문항에서 0.5퍼센트포인트의 차이는 표본 변동만으로도 생기므로,
정확도 두 개를 나란히 놓는 방식 대신 같은 문항을 두 모델이 푼 짝지은 비교인 McNemar 검정을 사용했습니다. 구현은 `scripts/compare_predictions.py`에
있으며, p값이 0.05를 넘으면 좋아졌다고 보고하지 않기로 규칙을 미리 정했고 9B 결합(④)이 그 규칙 덕분에 걸러졌습니다.

판정 기준도 언제나 실험을 시작하기 전에 고정했습니다. TTA와 dev 추가 학습에는 순증가 5문항 이상을 요구했고, Gemma QLoRA에는 bf16 zero-shot의
0.9695보다 0.005 높은 0.9745 이상을 요구했으며, InternVL3.5-38B에는 단독 0.9635 이상과 결합에서 3문항 이상 증가를 함께 요구했습니다. 최종 제출을
바꾸는 기준도 ⑳의 0.97765를 넘어야 한다는 조건으로 미리 정해 두었습니다. 결합 가중치는 Public 점수를 보고 탐색하지 않았습니다. ⑩은 언제나 0.5 대 0.5만 썼고,
⑳이 쓴 Gemma 가중치 0.4는 ⑲를 만들 때 fold 0 곡선을 보고 미리 고정해 둔 값을 그대로 옮긴 것입니다. 3B의 0.9144에서 27B 확대 LoRA의 0.9688까지
fold 0이 오르는 동안 Public도 0.89871에서 0.96931로 함께 올라, 검증 설계의 방향이 test와 어긋나지 않는다는 점도 확인했습니다.

## 4. 최종 방법 상세

### 4.1 세 재료의 설정

| 항목 | A (⑦) | B (⑧) | Gemma QLoRA |
|---|---|---|---|
| run-id | `colab27b_ft_bf16_v2_read_text_upscale` | `colab27b_ft_bf16_full_v2_read_text_upscale` | `gemma4_31b_ft_nf4_v2_read_text` |
| 모델 id | `Qwen/Qwen3.5-27B` | `Qwen/Qwen3.5-27B` | `google/gemma-4-31B-it` |
| revision | `fc05daec18b0a78c049392ed2e771dde82bdf654` | 같은 값 | `842da3794eaa0b77d5f08bae87a17459d91ff475` |
| 정밀도 | bf16 | bf16 | nf4, LoRA adapter는 bf16 |
| 해상도 | min_pixels 1,048,576 / max_pixels 2,097,152 | 같은 값 | 시각 토큰 1,120 |
| 학습 데이터 | fold 1~4의 5,358문항 | 전체 6,690문항 | fold 1~4의 5,358문항 |
| 설정 파일 | `configs/colab_qwen35_27b_bf16_upscale.yaml` | 같은 파일 | `configs/colab_gemma4_31b_nf4_lora.yaml` |

LoRA 하이퍼파라미터는 세 모델이 모두 같습니다. r이 16이고 alpha가 32, dropout이 0.05이며 학습률이 1.0e-4, epoch이 1, micro_batch가 1에
grad_accum이 8이어서 effective batch가 8입니다. scheduler는 linear이고 warmup_ratio가 0.03, weight_decay가 0.01,
max_grad_norm이 1.0, seed가 42입니다. LoRA는 언어 경로의 Linear에만 붙였습니다. vision tower와 merger에도 `q_proj` 같은 같은
이름의 모듈이 있어서 leaf 이름만으로 고르면 vision 까지 학습하게 되므로, `vqa/modeling.py`가 모듈 경로를 보고 language backbone 안의
Linear만 target으로 잡습니다. Gemma는 해상도를 바꾸는 키가 `processor_kwargs.max_soft_tokens` 하나이고 받을 수 있는 값이 70과 140,
280, 560, 1,120 다섯 개뿐이어서, 작은 글자를 살리기 위해 가장 큰 1,120을 썼습니다.

### 4.2 Gemma nf4 QLoRA와 양자화 제외 모듈

Gemma는 bf16 가중치가 약 62GB여서 21번 노트북이 쓰는 학습 하한(가중치 + 20GB = 82GB)이 A100 80GB 한 장을 넘어섭니다. 그래서 처음에는
zero-shot 추론만 수행했고, 2026-09-26 밤에 가중치를 nf4로 4bit 양자화해서 올리고 LoRA adapter만 bf16으로 학습하는 방식으로 이 제약을
우회했습니다. 하한이 `max(70 × 17/54, 17 + 20) = 37.0GB`로 내려가며 실제 preflight가 보고한 peak VRAM은 약 32GB로 80GB 안에 넉넉히
들어갔습니다.

양자화에서 제외한 모듈은 `model.vision_tower`와 `model.embed_vision`, 그리고 `lm_head` 세 개입니다. 앞의 두 개는 이미지 특징을 뽑는
계층이어서 4bit로 내리면 그 단계에서 이미 정보가 손실되고 그 손실은 언어 경로에만 붙는 LoRA로 되돌릴 수 없기 때문에 제외했습니다. `lm_head`를 함께 적어야 하는
까닭은 다릅니다. transformers의 quantizer는 `llm_int8_skip_modules`를 넘겨받으면 `get_keys_to_not_convert`가 계산하는 기본
제외 목록을 아예 쓰지 않으므로, 한 개라도 직접 적으면서 `lm_head`를 빠뜨리면 출력 계층까지 4bit로 내려갑니다. 이렇게 학습을 마친 Gemma의 fold 0 정확도는
0.9747(1310/1344)로 bf16 zero-shot의 0.9695(1303/1344)보다 7문항 높았고, 오답 margin도 0.904에서 0.825로 내려갔습니다.

### 4.3 결합 방식과 가중치

결합은 선택지별 확률을 가중 평균한 다음 가장 큰 선지를 답으로 고르는 방식이며, GPU를 쓰지 않고 CPU에서 확률 파일만으로 수행합니다. Gemma의 가중치를 0.4로 정한 근거는
fold 0에서 A와 Gemma 두 모델만으로 잰 곡선이고, 아래 값은 모두 A 단독(1302문항) 대비 정답 수의 증감입니다.

| Gemma 가중치 | 0.25 | 0.30 | 0.35 | 0.40 | 0.45 | 0.50 | 0.55 |
|---|---|---|---|---|---|---|---|
| A 대비 증감 | +2 | +3 | +5 | +8 | +9 | +5 | +4 |

곡선은 0.45에서 정점을 찍고 0.50부터 급격히 떨어집니다. 저희는 정점인 0.45가 아니라 0.40을 골랐습니다. 0.45의 +9문항과 0.40의 +8문항은 1문항 차이여서 잡음
범위 안에 있는 반면, 0.45는 점수가 떨어지기 시작하는 0.50 바로 옆자리라서 test에서 조금만 어긋나도 손해로 넘어갈 수 있다고 보았기 때문입니다. test에서도 Public
점수가 가중치 3분의 1에서 0.97348, 0.4에서 0.97616, 0.5에서 0.96723으로 움직여 같은 모양이 재현되었고, 비중을 0.55까지 올린 ㉑이 0.97378로
떨어져서 같은 판단이 다시 확인되었습니다.

## 6. 재현 방법

### 6.1 저장소 구조와 환경

모델을 다루는 코드는 모두 `vqa/` 패키지에 있고 노트북은 이 패키지의 명령을 호출하는 얇은 진입점입니다. 일회성 도구는 `scripts/`에, 설정은 `configs/`의
YAML 파일에, 노트북은 `notebooks/`에 두었으며 실행을 마친 노트북 사본은 `results/`에 보관했습니다. 팀 공식 fold CSV는 `fold_csv_files/`에
있고 데이터에서 파생된 산출물은 `artifacts/` 아래에 모입니다. 노트북은 `python scripts/build_notebooks.py`로 다시 생성하므로 변경 이력을
diff로 확인할 수 있습니다.

Colab A100 80GB에서 다음 조합으로 preflight와 학습을 통과했습니다. torch 2.11.0+cu128과 torchvision 0.26.0+cu128은 Colab
기본 이미지에 들어 있는 판을 그대로 썼고, transformers 5.16.1과 peft 0.20.0, accelerate 1.14.0, bitsandbytes 0.50.2,
pandas 2.2.3을 `requirements/colab.txt`로 고정했습니다. `requirements/colab-nodeps.txt`의 fla-core 0.5.2와
flash-linear-attention 0.5.2는 반드시 `--no-deps`로 설치합니다.

```
pip uninstall -y torchao
pip install -q -r requirements/colab.txt
pip install -q --no-deps -r requirements/colab-nodeps.txt
```

`torchao`를 먼저 제거하는 까닭은 Colab 기본 이미지에 들어 있는 0.10.0이 PEFT가 비양자화 Linear에 LoRA를 붙일 때 호환 오류를 내기 때문이고, 세 번째
줄을 `--no-deps`로 따로 두는 까닭은 fla 계열 패키지가 자기 의존성으로 torch와 triton을 다시 끌어오기 때문입니다. fla를 설치하지 않으면
transformers 5.16의 Qwen3.5 Gated DeltaNet이 예외 없이 PyTorch 참조 구현으로 내려가서 학습이 optimizer step당 58초로 느려집니다.

### 6.2 명령 순서

1순위 제출물 ⑳을 만드는 전체 순서는 다음과 같습니다. A는 `split_fold0.json`을, B는 `split_full.json`을 학습 분할로 쓰며, `--w-c 0.4`가
곧 A 0.3과 B 0.3, Gemma 0.4입니다.

```
python -m vqa.preflight --config configs/colab_qwen35_27b_bf16_upscale.yaml

python -m vqa.train --config configs/colab_qwen35_27b_bf16_upscale.yaml \
    --run-id colab27b_ft_bf16_v2_read_text_upscale \
    --split artifacts/data/split_fold0.json --set prompt_id=v2_read_text
python -m vqa.train --config configs/colab_gemma4_31b_nf4_lora.yaml \
    --run-id gemma4_31b_ft_nf4_v2_read_text \
    --split artifacts/data/split_fold0.json --set prompt_id=v2_read_text

python -m vqa.predict --config configs/colab_qwen35_27b_bf16_upscale.yaml \
    --run-id colab27b_ft_bf16_v2_read_text_upscale --csv test.csv \
    --adapter <RUN_ROOT>/colab27b_ft_bf16_v2_read_text_upscale/final_adapter \
    --out-name test_ft --set prompt_id=v2_read_text

python scripts/blend_preds.py \
    --a <RUN_ROOT>/colab27b_ft_bf16_v2_read_text_upscale/preds/test_ft.csv \
    --b <RUN_ROOT>/colab27b_ft_bf16_full_v2_read_text_upscale/preds/test_ft.csv \
    --c <RUN_ROOT>/gemma4_31b_ft_nf4_v2_read_text/preds/test_ft.csv \
    --w-c 0.4 --sample sample_submission.csv \
    --out-probs blend_A03_B03_Gq04_test_probs.csv --submission submission_A03_B03_Gq04.csv

python scripts/check_submission.py --submission submission_A03_B03_Gq04.csv \
    --sample sample_submission.csv --test test.csv
```

2순위 ⑲는 `--c`만 Gemma zero-shot 예측 `<RUN_ROOT>/gemma4_31b_base_bf16_v2_read_text/preds/test_base.csv`로
바꾸면 만들어집니다. 제출 파일은 예측 확률 파일에서 `vqa.submit`으로 결정적으로 재생성되므로, 같은 예측 파일과 같은 `sample_submission.csv`를 넣으면
언제나 같은 바이트의 제출 파일이 나옵니다.

상당 부분은 모델 성능이 아니라 라벨의 한계였다고 판단하며, 다만 이 추정은 56문항만 점검한 값이라 표본이 작습니다.

**둘째로 fold 0 1,344문항의 해상도가 부족했습니다.** fold 0에서는 QLoRA 결합이 zero-shot 결합보다 2문항 낮았는데 test에서는 약 10문항 높았습니다.
1,344문항에서 2문항은 0.15퍼센트포인트이고, 같은 fold 0에서 7문항 차이조차 McNemar p값 0.248로 표본 변동과 구분되지 않았습니다. Gemma의 전체 데이터
재학습을 접기로 했던 판단도 해상도가 부족한 검증셋의 값을 근거로 내린 것이므로, 검증셋을 넓히는 일이 남은 과제로 남습니다.

**셋째로 계열 다양성에는 강도라는 전제가 붙습니다.** 계열이 다르기만 하면 되는 것이 아니라 단독 강도가 적어도 A 수준에 닿아야 결합에서 이득이 났습니다. 0.9695였던
Gemma는 그 조건을 만족했고 0.9315였던 InternVL3.5-38B는 만족하지 못했습니다. InternVL은 A와 Gemma가 둘 다 틀린 22문항 가운데 5문항을 새로
맞혔지만 둘 다 맞힌 문항 가운데 55문항을 틀려서 잃는 몫이 훨씬 컸고, 8B에서 0.9345였던 값이 38B로 커진 뒤에도 그대로였다는 점까지 보면 이 계열은 이 과제의 한국어
OCR에 맞지 않는다고 판단합니다.

**넷째로 TTA는 검증에서 본 이득이 test에서 세 번 모두 뒤집혔습니다.** 선택지 순열 TTA4는 fold 0에서 A의 정확도를 0.9688에서 0.9710으로 올렸고

**다섯째로 80GB 제약을 양자화로 우회한 일이 점수를 바꾸었습니다.** Gemma는 bf16 가중치가 약 62GB여서 학습 하한 82GB가 A100 80GB 한 장을 넘어섰고
