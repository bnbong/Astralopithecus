# 발표 내용 정리

이 문서는 발표 슬라이드를 만들 때 넘길 내용 초안입니다. 디자인은 별도 도구에서 진행하므로,
여기에는 슬라이드마다 제목과 핵심 메시지, 화면에 올릴 수치와 그림, 발표 멘트의 요지만
적습니다. 숫자는 `results/README.md` 와 `docs/README_team.md`, 실행본 노트북의 출력에서
읽어 온 값만 사용했습니다. 아직 확인하지 못한 값은 `[확인 필요]` 로 표시했으므로, 슬라이드를
만들기 전에 그 자리를 먼저 채워 주십시오.

전체 분량은 11장입니다.

---

## 1. 문제 정의

**핵심 메시지**: 이미지 한 장과 질문 하나를 받아 네 개의 선지 가운데 하나를 고르는 한국어 VQA
과제이며, 이미지 속 글자를 읽어야 풀리는 문항이 큰 비중을 차지합니다.

**화면에 올릴 것**
- 과제 요약: 입력은 이미지 한 장과 질문 하나, 선지 a부터 d까지 네 개이고, 출력은 선지 하나입니다.
- 데이터 규모: train 6,714문항, test 6,714문항입니다.
- 평가 지표는 정확도입니다.
- 예시 이미지 두 장을 나란히 놓습니다. 한 장은 글자를 읽어야 풀리는 문항, 다른 한 장은 장면을
  이해해야 풀리는 문항으로 고릅니다.
- 문항 유형 분해 표를 넣습니다. fold 0 1,344문항 기준으로 `has_digits` 539문항,
  `korean_options` 602문항, `mostly_english` 152문항, `phone_like` 34문항, 그 밖이 17문항입니다.

**발표 멘트 요지**: 선지가 네 개뿐이라서 찍어도 25퍼센트는 맞습니다. 그래서 의미 있는 차이는
90퍼센트대 후반에서 갈립니다. 문항을 유형별로 나눠 보면 숫자나 영문 표기가 들어간 문항이 절반
가까이 되고, 이런 문항은 이미지 속 글자를 정확히 읽어야 풀립니다. 그래서 저희는 처음부터
"글자를 읽는 능력"을 기준으로 모델과 프롬프트를 골랐습니다.

## 2. 접근 전략

**핵심 메시지**: 모델 크기를 3B에서 9B를 거쳐 27B까지 단계적으로 올리면서 한계를 확인했고,
가장 큰 모델은 Colab에, 작은 모델은 실습실 PC에 배치해서 두 자원을 동시에 활용했습니다.

**화면에 올릴 것**
- 모델 크기를 단계별로 보여 주는 그림을 그립니다. Qwen2.5-VL-3B, Qwen3.5-9B, Qwen3.5-27B를 왼쪽에서 오른쪽으로
  배치하고, 각각 아래에 실행 환경을 적습니다.
- 자원 배분 표를 넣습니다. Colab A100 80GB에서 27B를 bf16으로 돌리고, 실습실 RTX 5060 Ti 16GB
  에서 9B를 NF4 QLoRA로 돌렸습니다.
- 학습 방식은 answer-only LoRA입니다. 정답 토큰 한 개만 감독하고, 나머지 위치는 모두 label
  mask로 가립니다.
- 결합 방식을 그림으로 보여 줍니다. 각 모델이 남긴 선지별 확률을 CSV로 캐시해 두고, GPU를 다시
  쓰지 않고 CPU에서만 가중치를 바꿔 가며 비교했습니다.

**발표 멘트 요지**: 자원이 두 종류였습니다. Colab의 A100은 빠르지만 세션이 언제 끊길지 모르고,
실습실 PC는 안정적이지만 VRAM이 16GB뿐입니다. 그래서 큰 모델은 Colab에, 작은 모델은 실습실에
맡기고, 두 결과를 확률 파일로 주고받는 구조를 먼저 정했습니다. answer-only LoRA를 쓴 이유는
선지 하나를 고르는 과제에서 문장 전체를 학습시킬 이유가 없었기 때문입니다.

## 3. 검증 설계

**핵심 메시지**: 고정된 fold 0 1,344문항에서만 모든 판단을 내렸고, 문항 단위 McNemar 검정으로
차이가 표본 변동인지 확인했습니다. 이 설계가 Public 점수와 잘 맞았습니다.

**화면에 올릴 것**
- 분할 규칙을 적습니다. 검증은 fold 0의 1,344문항이고, 학습은 train_fold1234의 5,358문항입니다.
  이 학습 분할에서는 test와 이미지가 같은 train 24문항을 미리 빼 두었습니다.
- 분할 파일의 내용 해시를 화면에 적어 둡니다. `artifacts/data/split_fold0.json` 의 해시는
  `ea2c8572...dfccae0` 입니다. 팀원 모두가 같은 분할을 쓰고 있는지를 이 값으로 확인했습니다.
- McNemar 검정을 설명하는 2×2 분할표 그림을 넣습니다. 한쪽만 맞힌 문항 두 칸이 핵심입니다.
- fold 0 점수와 Public 점수를 대조한 표를 넣습니다.

  | 모델 | fold 0 | Public |
  |---|---|---|
  | 27B 원본, 프롬프트 v1 | 0.9539 | 0.95889 |
  | 27B 학습, 프롬프트 v1 | 0.9568 | 0.96544 |

**발표 멘트 요지**: 1,344문항에서 0.5퍼센트포인트 차이는 표본 변동만으로도 생깁니다. 그래서
정확도 두 개를 나란히 놓는 것으로는 아무것도 판단할 수 없습니다. 같은 문항을 두 모델이 풀었으니
짝지은 비교를 해야 하고, 그 자리에 맞는 검정이 McNemar입니다. 저희는 p값이 0.05를 넘으면
"좋아졌다"고 보고하지 않기로 규칙을 정했습니다. 실제로 fold 0의 순위와 Public의 순위가 같은
방향으로 움직였기 때문에, 이 검증 설계를 끝까지 믿고 진행할 수 있었습니다.

## 4. 결과 1: 모델 크기

**핵심 메시지**: 모델을 키운 것이 가장 크고 확실한 개선이었습니다.

**화면에 올릴 것**
- 막대그래프 한 개를 그립니다. 가로축은 모델 크기, 세로축은 fold 0 정확도입니다. 세로축은
  0.90에서 0.97 사이로 잘라서 차이를 보이게 합니다.

  | 모델 | fold 0 정확도 |
  |---|---|
  | Qwen2.5-VL-3B (zero-shot, p2) | 0.9159 |
  | Qwen3.5-9B | 0.9464 |
  | Qwen3.5-27B (원본, v1) | 0.9539 |

- 9B 점수가 zero-shot인지 학습 이후인지 슬라이드에 함께 적습니다. `[확인 필요]`
- 3B의 Public 점수는 0.89871입니다. 9B의 Public 점수는 `[확인 필요]` 입니다.

**발표 멘트 요지**: 3B에서 9B로 갈 때 3퍼센트포인트가 올랐고, 9B에서 27B로 갈 때 다시
0.75퍼센트포인트가 올랐습니다. 올라가는 폭은 줄어들지만 방향은 분명합니다. 뒤에서 보여 드릴
프롬프트나 학습의 효과가 1퍼센트포인트 아래인 것과 비교하면, 저희가 쓴 방법 가운데 모델 크기가
가장 큰 변수였습니다.

## 5. 결과 2: 프롬프트와 OCR

**핵심 메시지**: 이미지 속 글자를 읽으라고 지시하는 프롬프트는 작은 모델에서 크게 도움이
되었지만 큰 모델에서는 효과가 거의 사라졌고, 외부 OCR 결과를 붙이는 방법은 기각했습니다.

**화면에 올릴 것**
- 프롬프트 두 종류를 나란히 보여 줍니다. v1은 이미지와 질문만 넣는 방식이고, p2(`v2_read_text`)는
  이미지 속 글자를 먼저 읽으라는 지시를 덧붙이는 방식입니다.
- 모델 크기별 효과 표를 넣습니다.

  | 모델 | 기본 프롬프트 | 글자 읽기 프롬프트 | 차이 |
  |---|---|---|---|
  | 3B | 0.8862 (p1) | 0.9159 (p2) | +3.0%p |
  | 27B 원본 | 0.9539 (v1) | 0.9591 (p2) | +0.5%p |

- 27B에서의 McNemar 결과를 함께 적습니다. v1만 맞힌 문항이 9개, p2만 맞힌 문항이 16개, 둘 다
  틀린 문항이 46개였고 p값은 0.23이었습니다.
- OCR 결합을 기각한 근거를 적습니다. OCR 텍스트를 붙였을 때 도움이 된 문항이 21개, 손해가 된
  문항이 24개였습니다.

**발표 멘트 요지**: 프롬프트로 "글자를 읽어라"라고 시키는 것은 모델이 그 능력을 이미 갖고 있을
때에는 의미가 없습니다. 3B에서는 3퍼센트포인트가 올랐지만 27B에서는 0.5퍼센트포인트에 그쳤고,
McNemar p값이 0.23이라서 통계적으로는 차이를 구분할 수 없었습니다. 외부 OCR도 같은 이유로
기각했습니다. 도움과 손해가 21 대 24로 맞물려서, OCR이 틀리게 읽은 글자가 모델을 오히려
헷갈리게 만드는 경우가 그만큼 있었습니다.

## 6. 결과 3: LoRA 학습

**핵심 메시지**: 학습은 fold 0에서 통계적으로 확인할 수 없는 크기의 개선을 주었지만, Public
점수는 분명하게 올랐습니다.

**화면에 올릴 것**
- fold 0 결과 표를 넣습니다.

  | 구성 | fold 0 | Public |
  |---|---|---|
  | 27B 원본, v1 | 0.9539 | 0.95889 |
  | 27B 학습, v1 | 0.9568 | 0.96544 |

- McNemar 결과를 적습니다. 원본만 맞힌 문항이 21개, 학습 모델만 맞힌 문항이 25개였고 p값은
  0.66이었습니다.
- 학습 설정을 적습니다. bf16, LoRA r=16, grad_accum 8, 670 step이며 step당 13.5초가 걸렸습니다.
- 학습 손실 곡선 그림을 넣습니다. `train_log.jsonl` 의 loss 값을 그대로 그립니다.
- p2 프롬프트로 같은 학습을 반복한 결과도 함께 적습니다. 원본이 0.9591, 학습 모델이 0.9583
  이었습니다. 다만 같은 프롬프트끼리의 McNemar p값은 아직 확인하지 못했습니다. `[확인 필요]`

**발표 멘트 요지**: fold 0에서는 0.3퍼센트포인트가 올랐고 p값은 0.66이었습니다. 저희 규칙대로면
"학습이 도움이 되었다"고 말할 수 없는 결과입니다. 그런데 Public 점수는 0.66퍼센트포인트가
올랐습니다. test가 6,714문항으로 fold 0의 다섯 배라서, fold 0에서는 표본에 묻혔던 차이가
test에서는 드러난 것으로 봅니다. 이 어긋남을 숨기지 않고 그대로 보고하는 것이 맞다고 판단했습니다.

## 7. 결과 4: 결합

**핵심 메시지**: 여러 모델의 확률을 결합하면 fold 0 점수는 올랐지만 통계적으로 확인할 수 없는
크기였고, 검증 점수만 보고 고른 조합이라 과적합의 위험이 있어서 최종 제출에는 넣지 않았습니다.

**화면에 올릴 것**
- 결합 후보 표를 넣습니다.

  | 후보 | fold 0 |
  |---|---|
  | ft_v1 단독 | 0.9568 |
  | ft_p2 단독 | 0.9583 |
  | ft_v1 + ft_p2 | 0.9576 |
  | ft_v1 + ft_p2 + 9B | 0.9613 |

- 가장 좋은 조합과 단독 모델을 비교한 McNemar p값은 0.48이었습니다.
- ft_v1과 ft_p2가 test에서 답이 갈린 문항은 93개였고, 선지 확률 차이의 평균은 0.0072였습니다.
- 각 후보의 Public 점수는 `[확인 필요]` 입니다. 결합 후보를 실제로 제출해 보았는지도 슬라이드에
  적어야 합니다. `[확인 필요]`

**발표 멘트 요지**: 결합의 전제는 모델들이 서로 다른 문항에서 틀리는 것입니다. 그런데 ft_v1과
ft_p2는 같은 모델에 프롬프트만 바꾼 것이라서, test 6,714문항 가운데 답이 갈린 문항이 93개에
불과했습니다. 확률 차이의 평균도 0.007 수준이었습니다. 서로 거의 같은 모델을 두 개 합친 셈이라
얻을 것이 적었습니다. 9B까지 넣으면 fold 0이 0.9613까지 올랐지만 p값이 0.48이었고, 여러 조합을
fold 0에서 비교해 고른 값이라 그만큼 검증셋에 맞춰졌을 가능성이 있습니다. 그래서 채택하지
않았습니다.

## 8. 한계 분석

**핵심 메시지**: 27B의 모든 변형이 공통으로 틀리는 47문항을 수빈 님과 창혁 님이 서로 다른
방식으로 각자 점검했는데, 두 사람의 판정이 서로 일치했습니다. 47문항 가운데 라벨 문제로
판정된 문항은 30문항 안팎이었고, 모델이 실제로 고칠 수 있는 오류는 16문항, fold 0 전체의
1.2퍼센트에 그쳤습니다. 그 16문항 중에서도 작은 글자·흐린 글자로 인한 오류가 9문항으로
가장 많았습니다.

**화면에 올릴 것**
- 겹침을 보여 주는 그림을 넣습니다. ft_v1이 틀린 58문항과 ft_p2가 틀린 56문항이 겹치는 부분이
  47문항입니다. 한쪽만 틀린 문항은 각각 11개와 9개뿐입니다.
- 47문항을 수빈 님이 이미지와 선택지를 직접 대조해 육안으로 점검한 결과를 표로 넣습니다
  (`artifacts/data/fold0_label_check_27b.csv`, `artifacts/data/fold0_label_check_27b.md`).

  | 판정 | 건수 | 비고 |
  |---|---|---|
  | 라벨 오류 | 6 | 모델이 고른 답이 실제로는 정답이었음 |
  | 애매함 | 23 | 이미지에 두 선택지 문구가 모두 있거나, 맞는 선택지가 없거나, 정답 보기에 오타가 있거나, 판독 근거가 부족함 |
  | 정답 맞음 | 17 | 실제로 모델이 틀린 문항 |
  | 미점검 | 1 | train_2411 |

  fold 0 1,344문항 기준으로 라벨 오류와 애매함을 합친 29건은 전체의 2.16퍼센트입니다.
  라벨 오류 6건을 정답으로 되돌리고 애매함·미점검은 그대로 오답에 남긴 보정 정확도는
  ft_v1이 1292/1321 = 0.9780, ft_p2가 1294/1321 = 0.9796입니다(하한값). 실제 모델 오류는
  17건, 1.26퍼센트입니다. test에도 같은 비율로 라벨 문제가 있다고 보면 Public 점수의 상한은
  약 0.978로 추정됩니다.
- 학습 모델(p2)이 높은 확신으로 틀린 문항을 세 개 골라 이미지와 함께 보여 줍니다. 이번에는
  육안 점검에서 "정답 맞음"(실제 모델 오류)으로 확인된 문항 중 확신도가 높은 세 개를 씁니다.
  `train_6299.jpg` 는 정답이 a인데 c를 0.998의 확률로 골랐고, `train_1000.jpg` 는 정답이
  a인데 b를 0.959로, `train_1476.jpg` 는 정답이 d인데 c를 0.958로 골랐습니다. 앞서 후보로
  삼았던 `train_3307`, `train_4748`, `train_1412`는 육안 점검 결과 앞 두 문항이 라벨 오류,
  마지막 문항이 애매함으로 판정되어 "모델이 확신하고 틀린 예시"로 쓰기에는 적절하지 않으므로
  제외했습니다.
- 애매함 23건의 유형은 네 가지로 묶입니다. 이미지에 두 선택지의 문구가 모두 있는 경우(10건),
  맞는 선택지가 없는 경우(8건), 정답 보기에 오타가 있는 경우(2건), 판독 근거가 부족한
  경우(3건)입니다. 정답 맞음 17건의 유형은 여러 대상 중 질문이 가리키는 것을 정확히 짚어야
  하는 경우(6건), 상호명과 판매 품목의 혼동(1건), 작은 글자·저해상도로 판독이 어려운
  경우(7건), 정답 보기의 오타 때문에 가장 가까운 답을 선택한 경우(2건), 기타(1건)입니다.
  창혁 님도 같은 47문항을 독립적으로 점검해 error_type과 라벨 오류 의심 여부로
  분류했습니다(임시본, 최종본이 아직 도착하지 않았습니다). 창혁 님의 임시본 분포는 작은
  글자·흐린 글자 19건, 기타 15건, 글자는 읽히는데 추론이 틀림 9건, 상식·외부 지식 3건,
  세기 1건입니다. 두 사람의 판정을 id 기준으로 합쳐서 얻은 consensus 분포는 아래
  표와 같습니다(임시본 기준 수치이며, 계산 방법은
  `artifacts/data/fold0_label_check_27b.md`와 `artifacts/data/fold0_error_types_27b.csv`에
  정리해 두었습니다).

  | consensus | 건수 |
  |---|---|
  | 라벨 문제 | 30 |
  | 모델 오류: 작은 글자 | 9 |
  | 모델 오류: 추론 | 7 |
  | 모델 오류: 기타 | 0 |
  | 미점검 | 1 |
  | 합계 | 47 |

  그림으로는 이 consensus 분포를 막대그래프로 보여 주거나, 위에서 정리한 교차표를
  그대로 화면에 띄우는 방식을 제안합니다.

**발표 멘트 요지**: 47문항을 그대로 "모델의 한계"라고 부르기 전에, 라벨 자체를 먼저
의심해야 했습니다. 수빈 님이 하나씩 육안으로 대조해 보니 29문항, 즉 47문항의 60퍼센트
넘게가 라벨 오류이거나 정답을 단정하기 어려운 애매한 문항이었고, 그중 라벨 오류로 확정된
6건은 모두 모델이 고른 답이 실제 정답이었습니다. 라벨을 보정하면 fold 0 정확도의 하한은
ft_v1 0.9780, ft_p2 0.9796까지 올라갑니다. 그렇게 걸러 내고 남은 실제 모델 오류는 17건,
1.26퍼센트뿐입니다. 이 17건은 두 선지 사이에서 망설이다가 틀린 것이 아니라, 0.9 이상의
확률을 한 선지에 몰아 주고 틀렸습니다. 이런 오답은 프롬프트를 바꾸거나 LoRA를 학습시키는
정도로는 바뀌지 않습니다. 더 큰 모델을 쓰거나, 라벨 자체를 다시 봐야 하는 영역입니다.
저희가 90퍼센트대 후반에서 더 올라가지 못한 이유의 상당 부분은, 실은 성능의 한계가 아니라
라벨의 한계였습니다.

## 9. 공학적으로 해결한 것

**핵심 메시지**: 모델 성능만큼이나 실행을 끝까지 살려 두는 일이 중요했고, 네 가지 장치로
해결했습니다.

**화면에 올릴 것**
- 네 가지를 각각 한 줄씩 적습니다.
  1. Colab 세션이 끊기는 문제는 분리 실행과 Drive checkpoint 재개로 해결했습니다. 오래 걸리는
     작업을 모두 `python -m vqa.jobs` 로 별도 프로세스로 띄우므로, 셀을 멈추거나 브라우저를
     닫아도 계속 돌아갑니다. 가상 머신이 회수되면 같은 셀을 다시 실행하기만 하면 마지막
     checkpoint에서 이어집니다.
  2. GPU 작업이 겹쳐서 메모리가 터지는 문제는 직렬화 가드로 막았습니다. `vqa.jobs start` 는 같은
     run-root에 살아 있는 job이 있으면 시작을 거부하고, `--min-free-gb` 로 지정한 만큼 여유
     메모리가 없어도 거부합니다.
  3. 몇 시간 뒤에야 드러나는 실패는 preflight로 미리 걸렀습니다. 15개 검사가 토큰과 템플릿,
     label 위치, 해상도 적용, 커널 경로를 한 번에 확인합니다.
  4. fla 가속 커널을 설치해서 학습을 4.3배 빠르게 만들었습니다.
- fla 전후 비교 표를 넣습니다.

  | 항목 | fla 없음 | fla 0.5.2 |
  |---|---|---|
  | 학습 microbatch | 7.3초 | 1.50초 |
  | 본 학습 optimizer step | 58초 | 13.5초 |
  | 문항당 추론 | 측정하지 않음 | 0.41초 |

**발표 멘트 요지**: 가장 인상적이었던 것은 네 번째입니다. transformers 5.16은 Qwen3.5의 Gated
DeltaNet을 전용 커널로 돌리려고 하는데, `fla` 패키지가 없으면 예외를 내지 않고 PyTorch 참조
구현으로 조용히 내려갑니다. 실행은 정상으로 끝나기 때문에, step당 58초가 걸리는 것이 원래
그런 줄 알고 하루를 썼습니다. 패키지 하나를 설치하고 나니 13.5초가 되었습니다. 지금은
preflight의 `kernel_fast_path` 검사가 같은 상황을 경고로 알려 줍니다.

## 10. 팀 역할과 일정

**핵심 메시지**: 다섯 명이 서로 기다리지 않도록 역할을 나누고, 게이트 조건으로 순서를
맞췄습니다.

**화면에 올릴 것**
- 역할 표를 넣습니다.

  | 팀원 | 역할 |
  |---|---|
  | 준혁 | 전체 통합과 Colab 27B 실행 |
  | 수빈 | 데이터 검사와 공식 split 확정 |
  | 유림 | 공통 학습 코드와 실습실 9B 학습 |
  | 창혁 | 프롬프트와 OCR, 해상도 결정 |
  | 수정 | 평가와 결합, 제출 검사 |

- 일정 그림을 넣습니다. 가로축을 날짜로 놓고 각자의 작업 구간을 막대로 그립니다. 실제 날짜와
  구간은 `[확인 필요]` 입니다.
- 게이트 조건을 두세 개 적습니다. 예를 들어 창혁이 입력 설정을 동결해야 27B base 캐시를 만들 수
  있었습니다.

**발표 멘트 요지**: 다섯 명이 GPU 두 대를 나눠 쓰는 상황에서 가장 위험한 것은 서로를 기다리는
시간입니다. 그래서 각자의 산출물을 파일로 정의하고, 그 파일이 나와야 다음 단계가 시작되도록
게이트를 걸었습니다. 예측 확률 CSV의 컬럼 순서까지 규칙으로 못 박은 것도 같은 이유입니다.
누가 만든 파일이든 같은 스크립트에 그대로 넣을 수 있어야 했습니다.

## 11. 결론과 남은 과제

**핵심 메시지**: 모델 크기가 가장 큰 변수였고, 학습은 Public에서 확인되었으며, 남은 47문항은
다른 접근을 요구합니다.

**화면에 올릴 것**
- 최종 성적을 적습니다. 최고 Public 점수는 0.96544이고, 기준선이었던 3B의 0.89871보다
  6.7퍼센트포인트 높습니다. 최종 순위는 `[확인 필요]` 입니다.
- 얻은 것을 세 줄로 정리합니다. 첫째로 모델 크기의 효과가 가장 컸습니다. 둘째로 프롬프트와
  OCR은 큰 모델에서 효과가 사라졌습니다. 셋째로 검증 설계와 통계 검정이 잘못된 결론을 여러 번
  막아 주었습니다.
- 남은 과제를 세 줄로 정리합니다. 첫째로 공통 오답 47문항을 유형별로 분석해야 합니다. 둘째로
  서로 다르게 틀리는 모델을 확보해야 결합이 의미를 갖습니다. 셋째로 p2 프롬프트의 원본 대비
  McNemar 검정을 아직 돌리지 못했습니다.

**발표 멘트 요지**: 저희가 얻은 가장 큰 교훈은 "올랐다"와 "확인되었다"를 구분하는 일이
생각보다 어렵다는 것이었습니다. fold 0에서 0.3퍼센트포인트가 올랐을 때 그것을 성과로 보고하지
않기로 한 결정이, 결과적으로 여러 잘못된 선택을 막아 주었습니다. 남은 시간이 더 있었다면 공통
오답 47문항을 먼저 들여다보았을 것입니다. 지금 저희가 가진 모델들은 모두 같은 자리에서
틀리기 때문에, 그 자리를 이해하지 않으면 무엇을 더해도 점수가 오르지 않습니다.
