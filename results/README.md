## 외부 OCR 결합을 기각한 근거 (2026-09-22)

창혁 님이 EasyOCR로 뽑은 텍스트를 프롬프트에 함께 붙이는 방식(p4)을 9B에서 측정한 결과,
정확도가 p2의 0.9479에서 0.9308로 1.7퍼센트포인트 떨어졌고 문항당 추론 시간은 0.66초에서
1.08초로 1.6배가 되었습니다. 27B 오답 가운데 OCR을 적용할 수 있었던 46건을 나누어 보면,
OCR이 글자를 읽어 낸 14건에서는 개선이 0건, 불변이 11건, 회귀가 3건이었고, 읽어 내지 못한
32건에서는 개선이 1건, 불변이 30건, 회귀가 1건이었습니다. 오답 유형이 "작은 글자·흐린 글자"
인 19건으로 좁히면 EasyOCR의 성공률은 21퍼센트(4/19)에 그쳤고, OCR 덕분에 정답이 된 문항은
0건인 반면 정답에서 오답으로 돌아선 문항은 2건이었습니다. 모델이 읽지 못하는 글자는 OCR도
읽지 못하므로, 병목은 글자를 텍스트로 옮기는 단계가 아니라 모델에 들어가는 픽셀에 있습니다.
그래서 OCR 결합을 기각하고, 남은 수단인 작은 이미지 확대(`min_pixels` 상향)를 시도하기로
했습니다. 작은 글자로 틀린 12문항의 원본 크기를 직접 재 보니 10문항이 720×960 또는 960×720
이고 나머지 두 문항은 720×1280과 720×720이어서 12문항 모두 기존 상한인 1,048,576픽셀 아래에
있었으므로, 상한(`max_pixels`)을 올리는 방법으로는 이 문항들의 입력이 바뀌지 않습니다. 상세 판정은
`experiments/ocr/test_result/ocr_verification_result.csv` 에 47행으로 남아 있습니다(위 46건에 OCR
적용 대상이 아닌 1건을 더한 수입니다). 저장소에는 포함하지 않으며 팀 내부에서만 보관합니다.

유림 님이 dev 이미지 30장으로 PaddleOCR과 EasyOCR을 실습실 CPU에서 별도로 비교했을 때도
같은 결론이 나왔습니다. 사람이 판정한 결과는 Paddle 우세 26장, 동률 2장, Easy 우세 1장,
둘 다 실패 1장이었고, EasyOCR은 30장 가운데 13장이 수동 평가에서 활용 불가(X) 판정을 받았으며,
그중 출력 문자열이 완전히 빈 경우는 6장이었습니다. Paddle이
EasyOCR보다 뚜렷하게 나은 엔진임을 확인했더라도, 위에서 측정한 9B·val_fold0 실험의
결론(OCR이 맞게 읽은 14건에서 개선 0건, 회귀 3건)은 바뀌지 않습니다. 즉 OCR 엔진을
바꾸는 것만으로는 VQA 정확도가 오르지 않으며, 병목은 여전히 모델에 들어가는 픽셀 해상도에
있습니다. 다만 모델이 못 읽는 작은 글자 12건 가운데 일부를 Paddle이 읽어 낸 사례는, 해상도
확대 실험 결과에 따라 별도로 검토할 필요가 있습니다. 원본 비교 데이터는
`artifacts/data/ocr_engine_comparison_30.csv` 에 30행으로 정리해 두었습니다.

본 학습의 optimizer step을 기준으로 보면 58초에서 13.5초로 줄었으므로 약 4.3배 빨라졌습니다.
두 측정은 모두 같은 A100 80GB에서 27B를 bf16으로 올리고 LoRA r=16, grad_accum 8로 돌린
결과입니다.

속도가 이만큼 갈린 원인은 커널 선택에 있습니다. transformers 5.16의 Qwen3.5 Gated DeltaNet은
`chunk_gated_delta_rule` 을 Hub 커널로 부르는데, `transformers/integrations/hub_kernels.py` 의
`use_kernel_func_from_hub_with_fallback` 이 커널을 불러오지 못하면 예외를 내지 않고 PyTorch
참조 구현으로 조용히 내려갑니다. 이 경로를 담당하는 패키지가 `fla` 이므로, `fla` 가 설치되어
있지 않으면 학습과 추론이 모두 참조 구현으로 돌아가면서 위 표만큼 느려집니다. 경고 로그만
남고 실행은 정상으로 끝나기 때문에, 속도를 직접 재 보기 전에는 알아채기 어렵습니다.
